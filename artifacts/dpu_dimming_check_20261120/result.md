# Digital dimming на GLOBAL: флаг выбирает объект, но не включает весь тракт

**На XT2611-1 / GLOBAL W3WWS36.65-64-4-1 найден независимый от флага порог: `DigitalDimming::Init` принимает `kPanelMaxBl` только в диапазоне 1…8191.** У выбранного BOE ILI97701A `cmd_v4` максимум DT и архивный sysfs — **16180**. Если HAL возвращает это же число, инициализация завершается `-EINVAL` ещё **до** загрузки калибровки. Сам ответ HAL в живом вызове не записан. Предпочтительный обратимый опыт — штатный Extra Dim против равнояркого серого, без изменения vendor property или DDIC.

### Что показали файлы

- **Идентичность** (`confirmed-on-target` — прежнее получение отпечатков и значения property; анализ ниже — `reported`). Локальный CN11 `vendor_a/lib64/libdigital-dimming.so` — 100360 байт, SHA-256 `76226a517d45170d7a204cc7337e627ee4ac59b99095aad8ebce57aca275acf1`, равен [отпечатку точной OTA](../brightness_policy_recon_20261107/target_userspace_comparison.json#L31-L38). Прежний target getprop = `1`. [Фабрика](../brightness_policy_recon_20261107/result.md#L60-L88) читает `vendor.display.disable_stc_dimming` при создании: absent/ненулевой `atoi` → Default; присутствует и `atoi==0` → полная реализация. Это не наблюдение горячего переключения уже созданного объекта.
- **Новая проверка кода.** В Ghidra 12.1.4, `DigitalDimming::Init` (ELF VA `0xcc64`, строки декомпилята 146–188, 180–227, 226–291, 565–606), виртуальный `GetParameter(0)` заполняет 4-байтовый payload. На успехе проверяется `uint32(max−0x2000) < 0xffffe001`; истинная ветвь пишет `Invalid max_bl` и возвращает `−22`. Границы проверены отдельно: 0/8192/16180 отклоняются, 1/8191 проходят. Это **максимум интерфейса**, не текущий DBV слайдера. [Readback 16180](../exact_dbv_dispatch_20261106.json#L72-L77) согласуется с обеими ячейками `qcom,mdss-{brightness-max-level,dsi-bl-max-level}` в [выбранном DT](../device_tree/selected_boe_v4/).
- **Откуда значение.** В `libsnapdragoncolor-manager.so` из CN11 и раннего RETEU (побайтово одинаковы) `BlScaleImp::Init` (`0x1e28c`) кеширует ответ слота `+0x238` без масштабирования; `GetPanelBlMaxLvl` (`0x1e8ac`) отдаёт это поле `+0x34`. В [точных GLOBAL core/DAL](../brightness_policy_recon_20261107/target_userspace_comparison.json#L15-L30): `DisplayBuiltIn` vtable `0xe0778 + 0x238` → `DisplayBase::GetPanelBlMaxLvl` → слот `+0x198` single/multicore → слот `+0x198` периферии. `HWDeviceDRM::GetPanelBlMaxLvl` (`0x3bcf0`) возвращает поле **u32 `+0x67c`**. Напротив, `HWPeripheralDRM::GetHWPanelMaxBrightness` (`0x51524`, строки 95–145) открывает `…/max_brightness`, читает через `pread` и кладёт `atof` в **float `+0x48c`**. Это разные поля: архивный sysfs сам по себе не доказывает отказа. Для DAL использован RETEU ELF, SHA-256 совпал с OTA. Идентичность **менеджера** с OTA и фактическое значение `+0x67c` — `unknown`; различающий пассивный маркер — сообщение core `Got panel max backlight %d` того же дисплея/сборки.
- **Калибровка — второй независимый барьер.** В полном `Init` требуются непустые интерфейсы, загрузчик `libbacklight-calib.so`, `dlsym` фабрики `GetBackLightNitsFactoryIntf`, создание и успешный `Init` её объекта. При `−2` логируется `Missing XML for backlight calib`; вычисление LUT находится в отдельной ветви `ret==0`. При свежем просмотре `/vendor/etc/display/` в CN11 только один `backlight_calib_*.xml`, для **NT37802**, в раннем RETEU **ни одного** (38 regular entries, BOE QDCM JSON присутствует). RETEU — `XT2611-3 W3WW36.65-64-4`, vendor_a из локального service ZIP, проверено покрытие extent 1415241728/1415241728 байт. Состав `/vendor` и `/odm` точной OTA для этого XML — `unknown`; цветовая C3D-калибровка не заменяет backlight XML.

### Ближайший различающий опыт (`hypothesis`, не запускался)

[Extra Dim, сила 50](../stock_extra_dim_locked_20261118/result.md#L3-L17) уже давал `RGB 1 → 0,522 → 1` при DBV 828 / 120 Гц. Первый оптический проход отклонён из-за ISO; при фиксированном ISO изменялся растр **фото прибора**, а не измеренная частота. [Контроль серым](../night_r079_r081/result.md#L7-L11) остановился до снимка. В R28 на тёмном сером [0/12 кадров прошли допуск по сигналу](../ddic_r28_requalification_20261120/result.md#L3-L18); «серый неизбежно возвращает полосы» этим архивом не доказано.

На одном низком DBV, в SDR, с неизменными фактическим refresh и исходным профилем панели (Flicker prevention OFF): **A** — белый + штатный Extra Dim 50; **B** — Extra Dim OFF + серый, заранее подобранный по среднему DC-сигналу фотодиода за вычетом тёмного. 133/191 — лишь стартовые коды. Сначала белый OFF и закрытый датчик для проверки оптической связи и диапазона; затем независимые блоки AB/BA с повтором той же фазы (sham). В каждом окне сверять матрицу SF, DBV и режим. При одинаковом среднем в пределах заранее измеренной повторяемости сравнить минимум, огибающую и интервалы на двух развёртках. Разница сверх sham означает зависимость от способа затемнения в этой точке, но не локализует её в FRC или DDIC. Нет согласования среднего или валидного оптического канала с достаточной полосой — `unknown`. Возврат по таймауту: исходные значения ключей (отсутствовавшие удалить), сцена и повторная сверка матрицы/DBV/режима. Новых обращений к устройствам: **0**.

Для воспроизведения кода использован `06-tools/ghidra_decompile.py decompile <ELF> --address <import VA> --lines A:B --output <внешний каталог>`; для этих ET_DYN `import VA = ELF VA + 0x100000`, для ET_REL выбрать `--function reg_dmav1_setup_dspp_pcc_common`. Адреса выше не runtime VA.

### Дополнение: проверка на текущей OTA после офлайн-разбора

`confirmed-on-target`: через привязанный ADB прочитаны `/vendor/lib64/libsnapdragoncolor-manager.so` (SHA-256 `d9119d8873f2f0428ecc829044bf1b6bb8a72a7b4e5e660a4c02865964c79b81`) и `/vendor/etc/display/qdcm_calib_data_mipi_mot_cmd_boe_1440p_dsc_682.json` (`bda2618a08c53244d90a913c167d40ba386e954f02737ef6423bf79e735ca1db`): оба совпали с проверенными CN11-файлами. То есть проверки **содержимого** менеджера и профилей выше применимы и к этой OTA; текущий итог после merge и FRC панели всё ещё неизвестны. SHA-256 текущей `libdigital-dimming.so` также совпал, флаг остался `1`.

Имен `*backlight*calib*.xml` под `/vendor/etc/` и `/odm/etc/` не найдено; в `/vendor/etc/display/` есть отдельные BOE PCC/C3D-файлы. Это не исключает другие имена/пути. При пассивной проверке последних 5000 сообщений main/system не получен атрибутированный результат `GetPanelBlMaxLvl`; статус полного `Init` остался неизвестен. Вместо переключения HAL [R32](../scope_baselines_r32_20261120/result.md) проверил штатный Extra Dim на **высоком** фиксированном BL: реально изменились RGB-коэффициенты, устойчивый интервал на растре не исчез; равенство средней яркости и процент модуляции по AC не измерены.
