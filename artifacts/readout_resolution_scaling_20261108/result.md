# Старый stock 720p → 4K → 720p: нормировка по строкам, offline

`confirmed-on-target` относится к архивной съёмке панели, не к частоте OLED.
Использованы только три уже сохранённых [видео](../pacman_readout_capture_20261106.json)
`../optical/pacman_readout_{A1,B,A2}_20261106.mp4`: stock DBV3600,
DC OFF, requested120; Pacman 100 µs/ISO6400, nominal30fps, reported
rollingShutterSkew15047630ns. Ни телефон, ни камера не включались.

## Проверяемая гипотеза и метод

Если fine-полосы в 4K занимают втрое больше **выходных** строк, чем в 720p,
съёмка в двух разрешениях даёт ту же нормированную пространственную частоту,
а не независимое уравнение для неизвестного sensor-row mapping. Другое отношение
могло бы указать на изменение camera mode или самого наблюдаемого рисунка.

[Воспроизводитель](analyze.py) извлекает исходную Y-плоскость HEVC, не
конвертирует диапазон через `format=gray`: центральные кадры90–214 каждого
клипа, три перекрывающихся 75-кадровых окна90–164/115–189/140–214. В 720p
ROI `x540:600,y190:690` (60×500), в 4K геометрически втрое увеличенная
`x1620:1800,y570:2070` (180×1500). Это предположение о совпадении FOV,
не измерение физического crop/sensor mode. Усреднение по x, Legendre detrend2,
Hann FFT через существующий `06-tools/optical_spectrum.py`. Пики ищутся
в заранее заданных fine-диапазонах `h×[0.008,0.014]` cycles/720p-equivalent row,
`h=1,2,3`. Все27 пиков внутренние, ROI без насыщенных Y-пикселей.
Численные результаты/условия/ограничения: [analysis.json](analysis.json).

| Этап, разрешение | Fine period в строках видео, окна90–164/115–189/140–214 | Fine period после приведения к 720p |
|---|---|---|
| A1 720p | 94.16 / 94.16 / 93.09 | 94.16 / 94.16 / 93.09 |
| B 4K | 282.48 / 280.07 / 277.69 | 94.16 / 93.36 / 92.56 |
| A2 720p | 93.09 / 93.09 / 93.09 | 93.09 / 93.09 / 93.09 |

Для дополнительного контроля приведённые 2-я/3-я image-компоненты лежат
соответственно в диапазонах46.48–47.08 и31.03–31.27 строк при всех трёх
разрешениях/окнах. Анализ описывает пространственные циклы *в закодированном
видео*, не физические гармоники панели. Сдвиг ~1–2% между окнами и возвратом
сохранён, а не скрыт единым числом.

## Следствие и границы

`V/P_output` примерно сохраняется при `V=720→2160→720`. При неизменном
15.047630ms camera skew это не даёт второго независимого ограничения на
неизвестный `N_eff` в модели [readout ambiguity](../optical_readout_ambiguity_20261108.md):
`f = V×H/(P_output×skew×N_eff)`. Эквивалентный период ~93–94 строки **не**
частота720/1440/2160/≥2000Hz; encoder resampling, camera ISP, физический
гармонический порядок и настоящий sensor timestamp остаются неизвестными.
Равный геометрический ROI не доказывает один sensor mode, а encoded PTS не
квалифицированы как момент экспозиции. Окна выбраны по журналу start/hold,
не сопоставлены с per-frame аппаратными timestamps; источник полос может быть
камерой, сценой либо дисплеем.

Этот отрицательный результат закрывает только надежду откалибровать физические
Hz **одним изменением выходного разрешения** архивной съёмки. R3 остаётся
active; A9-only — прежний промежуточный baseline q93 ratio0.2264067,
не Hz. A0D1C1 не авторизован/не запускался; новых DSI или других аппаратных
операций не было.

Проверка: независимый review декодировал native Y без нашего фильтра и подтвердил
все41 250 000 пикселей ROI,27 пиков и их RMS прямыми Fourier-суммами с
независимым QR detrend (максимальное расхождение8.88×10⁻¹⁶ Y-кода);
пространственная автокорреляция также дала масштаб3×. Собственный повтор
воспроизвёл JSON побайтно; обычный Python и `-O` отказались перезаписать его,
сохранив bytes/mtime. Синтаксис, ближайшие ссылки и отсутствие A0D1C1
authorization/run проверены.

## Офлайн-контроль геометрии изображения

[Отдельный воспроизводитель](geometry_check.py) извлёк **исходную Y-плоскость**
кадров125/150/175 тех же трёх видео. Кадры4K приведены к1280×720 усреднением
ровно3×3 пикселей, без конвертации диапазона. В каждом кадре измерены две
горизонтальные границы изображения экрана по x-профилю на y190:690 и верхний
переход по контрасту «экран x300:650 − фон x900:1100»; соответствующие окна
поиска выбраны после предварительного просмотра кадра150 и затем **не менялись**
для девяти кадров. [Числа и пределы](geometry_check.json):

| Серия | Левая/правая границы x на нормализованных кадрах | Верхний переход y | Корреляция x-профиля с A1 того же индекса |
|---|---|---|---|
| A1 720p | 136–138 / 744 | 51–58 | 1.000 |
| B 4K→720p | 136–139 / 744–747 | 53–55 | 0.99878–0.99907 |
| A2 720p | 136–138 / 747 | 52–54 | 0.99980–0.99991 |

`confirmed-on-target` **только для изображения**: в этих выбранных кадрах
экран занимает практически одинаковые нормализованные координаты, включая
вертикальный ориентир. Это усиливает геометрическую основу сравнения периодов
~94/280/93 строк, но **не** доказывает один и тот же sensor mode, число
активных считываемых строк `N_eff` или миллисекунды на строку. Фаза/содержание
полос и UI могут сдвигать границы на несколько пикселей; равенство всей FOV
и физические OLED Hz не заявлены. R3 active, A9-only baseline неизменен,
A0D1C1 по-прежнему требует отдельного подтверждения; аппаратных действий нет.
Независимое review покадрово декодировало native Y без `select` и подтвердило
побайтовое совпадение девяти кадров, идентичный3×3 downsample и все границы;
максимальное расхождение корреляций5.6×10⁻¹⁶. `geometry_check.py` воспроизводит
JSON побайтно; normal/`-O` не перезаписывают существующий результат.

## Офлайн-проверка метаданных в самих MP4

Гипотеза: покадровые данные или HEVC SEI в этих трёх **сохранённых** видео
могут сообщить sensor mode/время строки и устранить неизвестный `N_eff`.
`ffprobe -show_entries format_tags:stream=index,codec_type:stream_tags:frame=side_data_list
-of json` не нашёл frame side data; ключи format/stream tags ограничены
обычными Android model/manufacturer/version, creation/handler/language и
MP4-brand. Значения идентификаторов не публиковались. Публичных ключей
sensor mode, rolling shutter или line duration нет.

Дополнительно `ffmpeg -map 0:v:0 -c:v copy -bsf:v hevc_mp4toannexb -f hevc`
вывел видеопотоки в память, без перекодирования. Разбор NAL start codes и
`(first_header_byte >> 1) & 63` дал:

| Видео | NAL type 1 | type 19 (I) | type 32/33/34 (VPS/SPS/PPS) | SEI type 39/40 |
|---|---:|---:|---:|---:|
| A1 720p | 334 | 15 | 15/15/15 | **0/0** |
| B 4K | 335 | 15 | 15/15/15 | **0/0** |
| A2 720p | 334 | 15 | 15/15/15 | **0/0** |

Проверка ASCII-строк `rollingShutterSkew`, `sensorMode`, `sensorReadout`,
`lineDuration` и текстового `15047630` в исходных MP4 также не дала совпадений.
Это закрывает **только** поиск явной sensor-row metadata в перечисленных
format/stream/frame fields, HEVC SEI и этих текстовых ключах. Не доказано
отсутствие бинарных vendor-полей контейнера или доступности timing через
camera HAL/документацию; SEI/VUI с frame cadence не были бы сами по себе
измерением sensor-row time. Численная OLED PWM частота остаётся неизвестной,
R3 active, A9-only intermediate; A0D1C1 не разрешён и не запускался.

## Контроль простого трёхкратного апскейла

На кадрах125/150/175 4K видео B проверено, можно ли восстановить Y-плоскость
в экранной области `x500:2100,y220:1720` из каждой третьей строки и колонки
билинейной интерполяцией. Минимум по девяти фазам решётки даёт RMS остатка
**0.785/0.797/0.785 Y-кода**, а доля пикселей с `|остаток|>2` равна
**2.13/2.33/2.15%**. Иллюстративный контроль — синтетический 3× nearest
repeat фрагмента A1, **не прошедший 4K HEVC encoding**, — даёт RMS
**0.469/0.434/0.451 Y-кода** тем же методом. Разность не доказывает
отсутствие апскейла: кодек, ISP/sharpening и иной алгоритм интерполяции
неотделимы от исходных отсчётов. Следовательно, и этот тест не определяет
`N_eff`, время строки или физические PWM Hz. Исходные видео и устройства
не менялись; R3 остаётся active.

## Отдельный контроль широкой движущейся полосы (сохранённые видео)

`hypothesis`: если широкий рисунок принадлежит тому же устойчивому временному
источнику и та же геометрия считывания сохраняется, его период в 4K должен
быть примерно втрое больше в **выходных** строках и сохраняться после
приведения к 720p. Это не проверка физического фундаментала или частоты OLED.

Повторно использованы только кадры90–214/ROI из [воспроизводителя fine](analyze.py)
при stock DBV3600/DC0/requested120 и Pacman100µs/ISO6400. Для каждого из трёх
перекрывающихся75-кадровых окон измерен максимум в исторической широкой
полосе `0.0023…0.0053 cycles/720p-equivalent row`: исходные row-профили
`raw` и отдельно `moving_only` (вычитание среднего профиля **каждого окна**),
Legendre detrend степеней1/2/3 и Hann FFT. Таблица — периоды, приведённые
к720p, только центральное окно115–189; порядок столбцов — detrend1/2/3:

| Сток-клип | Raw, строки720p | Moving-only, строки720p |
|---|---|---|
| A1 720p | 273.07 / 227.56 / 195.05 | 256.00 / 227.56 / 199.80 |
| B 4K | 273.07 / 237.45 / 195.05 | 254.02 / 237.45 / 198.59 |
| A2 720p | 315.08 / 256.00 / 221.41 | 303.41 / 248.24 / 215.58 |

У B сырой центральный degree2 период **~712.35 строк4K** (237.45×3),
но при неизменном720p A1→A2 он также сдвигается227.56→256.00 строк.
Во всех 54 сочетаниях window/mode/detrend приведённые периоды лежат
~195.05…431.16 строк; два поздних A2 degree1 пика попадают на нижнюю
границу band. На500 строках широкий диапазон содержит лишь~1.15–2.65 цикла;
вычитание stationary profile не доказывает, что осталась одна физическая
компонента. Detrend и время меняют максимум гораздо заметнее, чем у
fine-полосы~93–94 строки. Нельзя выделить из этих видео причинный эффект
разрешения камеры, физический источник broad или низкочастотную огибающую;
нет независимой camera-row timebase и нет измерения PWM Hz. A9-only q93
ratio0.2264067 остаётся лучшим **panel**, а не camera, baseline; R3 active.

Воспроизведение 54 записей (чтение трёх уже сохранённых видео, без device I/O;
печатаются `период720p, RMS амплитуда Y, на границе band`):

```sh
PYTHONDONTWRITEBYTECODE=1 OPENBLAS_NUM_THREADS=2 python3 - <<'PY'
import importlib.util, json
from pathlib import Path
p = Path('artifacts/readout_resolution_scaling_20261108/analyze.py')
s = importlib.util.spec_from_file_location('saved_readout', p)
m = importlib.util.module_from_spec(s)
s.loader.exec_module(m)
for c in json.loads(m.SOURCE.read_text())['clips']:
    label = c['label']
    v, x, y, w, h, fft = m.GEOMETRY[label]
    profiles = m.decode(m.ROOT / c['video'], x, y, w, h).mean(axis=2)
    for first, last in m.WINDOWS:
        window = profiles[first - 90:last - 89]
        for mode in ('raw', 'moving_only'):
            signal = window if mode == 'raw' else window - window.mean(axis=0, keepdims=True)
            for degree in (1, 2, 3):
                peak = m.analyze_profiles(signal, n_fft=fft,
                    frequency_min=.0023*720/v, frequency_max=.0053*720/v,
                    detrend_degree=degree, peak_count=1)['peaks'][0]
                print(label, first, last, mode, degree,
                    round(peak['period_rows']*720/v, 2),
                    round(peak['total_rms_amplitude'], 3),
                    peak['at_frequency_boundary'])
PY
```

Независимое offline-review повторно извлекло все41 250 000 native-Y пикселей,
пересчитало все54 пика прямыми Fourier-суммами с QR-detrend и подтвердило
18 чисел таблицы (максимальная разница RMS 5.44×10⁻¹⁵ Y-кода). Проверка
синтаксиса/ссылок и запуск приведённой команды подтвердили границы и два
поздних A2 edge-пика. Аппаратная частота этим не квалифицирована.
