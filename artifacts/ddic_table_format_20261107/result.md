# DDIC table format: проверка по сырым архивным ответам

2026-11-07. **R3 active; физический PWM ≥2000 Гц не установлен.**
Новая гипотеза: формат блоков `51/52/53/63` позволит отличить таблицу числовых
коэффициентов от программы секвенсора и получить осмысленный emission-параметр.
Работа только офлайн; старые readers не запускались. A9-only baseline и исходные
оптические записи сохранены, A0D1C1 не авторизован и не исполнен.

## Что действительно проверено

`confirmed-on-target` относится к происхождению прежних DT/чтений;
следующие выводы — `reported`, новый воспроизводимый анализ этих файлов.

1. Десять payload из actual native OFF (`51:A1/A2`, `52:81/82`, `53:95/A2`,
   `63:F1–F4`) совпадают с **префиксами** ответов в обоих проходах каждого из
   четырёх архивов: DBV3584/120, DBV3646/120, DBV3584/144, DBV3584/60.
   Проверены raw.txt, а не только производные registers.json: **80 совпадений**.
2. Для каждого из восьми проходов совпадают первые шесть байтов соответствующих
   opcode в четырёх соседних восьмикомандных окнах:

   | Page | Начала четырёх совпадающих окон |
   |---|---|
   |51|80,88,90,98|
   |51|A0,A8,B0,B8|
   |51|C0,C8,D0,D8|
   |52|80,88,90,98|
   |52|A0,A8,B0,B8|

   Это **40 проверок квартетов**, не доказательство двадцати независимых банков.
   Одинаковые ответы совместимы и с aliases, и с копиями данных. Write aliases
   и автоматическое увеличение адреса не установлены.
3. Условная раскладка шести байтов как четыре low-byte и два упакованных
   high-nibble даёт, например, `51:A1 OFF → [0x244,0x244,0x279,0x27b]`.
   Но на четырёх изменяемых шестибайтовых payload **оба порядка high-nibble
   неразличимы**: хвосты `22 22` или `00 00` симметричны. Поэтому это не
   восстановленный decoder и не доказательство gamma, периода или счётчика.

Результат: [analysis.json](analysis.json), воспроизводитель [analyze.py](analyze.py).
Номера исходных raw-строк включены в JSON. Запрошенные сорок байтов не стали
доказанной длиной ответа; нулевые хвосты не используются как карта регистров.
Порядок `53:F0=1 → 63:F1..F4 → 53:F0=0` остаётся известной последовательностью
записей, **не декодированной программой CMDQ**.

## Проверка альтернативного источника

Чтобы не ограничиваться названиями двенадцати знакомых файлов, получен полный
публичный source archive `MotorolaMobilityLLC/kernel-display-devicetree` на pin
`f088523dfba85c95c15f43726fcf972c0c7a957a`: 260682 compressed bytes, **407 файлов**.
Размеры и Git blob IDs всех файлов проверены против ранее сохранённого полного
tree manifest. Архив не распаковывался по произвольным путям.

Ключ `FF 5A A5` найден в прежних 12 ILI97680A/ILI97701A файлах и четырёх board
overlays (`alor-sde-display-{avr,eletre,vantage}`, `canoe-sde-display-vantg`).
Безымянного дополнительного DDIC с объяснённым форматом в этом корпусе не найдено.
Это охват **одного pin**, не всех опубликованных версий.

Полный `git ls-remote --heads --tags` дал 902 строки (включая peeled annotated tags). Дополнительно
проверен ранее не выбранный тег `MMI-W3WLS36.46-2-9-2`, peeled commit
`c9e8fc8fa4c31efb50e9f88e51ef255edfe0fb5b`: 140 файлов, 130 в display/.
В нём нет искомого ключа или ILI97/BOE paths; среди panel-файлов — CSOT NT37707.
Похожее имя сборки не является источником target-регистров или flash-совместимости.

Проверены также два других конкретных Android16 heads:
`w3wb36.36-48-5` → `3a248241db09b1d39d12b90beb8c9bbf55e8fdc9` и
`w2wv36.55-25-15` → `9cd55ea324c7d75e157f06a27f03fb447dea9fc0`.
Второй содержит семь побайтно прежних ILI97680A-файлов. В первом девять ILI97
файлов совпали с f088; отличается только более ранний ILI97701A v2, без v3/v4.
У него ещё есть `02:AB B0 82 / 20 83`. Уже сохранённый patch
`ddic-4f-followup-20261107/ed79f62ad71cce156318fcc58cf38c9965ebae09.patch`
удаляет именно эти записи вместе с изменением **90Hz MIPI timing**
(clock925MHz→1234MHz, transfer-time7933us). Это не новый emission-профиль;
ни смысл AB, ни формула PWM из сопутствующей MIPI-правки не следуют.
Новые source archives не подставлялись в target DT.

Отдельный внешний RECON проверил donor CSOT ILI7838A:
`LineageOS/android_kernel_motorola_sm7435-devicetrees`, pin
`b5608a3128f610aed19037120791abe632fcc4f9`,
`display/dsi-panel-mot-csot-ili7838A-667-1080x2400-dsc-cmd-common.dtsi:93–130`.
Его ключ `FF 78 38` отличается; `53 20` на page00 — не target page53:F0.
Прямого gamma decoder/описания секвенсора этот donor не дал; его байты не переносились.
Sourcegraph C-prefix поиск ограничен индексом и shard limits, GitHub commit-search
частично отвечал403. Это не доказательство глобального отсутствия документации.

Малые source archives, refs и JSON проверки корпуса сохранены в
`/home/stfu/.cache/opencode-tmp/opencode/ddic-table-format-20261107/`.

## Проверки и следующий переход

- Воспроизводитель прошёл все восемь архивных проходов. Независимое ревью
  отдельно разобрало DT packets, 80 prefixes и 40 quartets; замечаний нет.
- Reviewer проверил семь in-memory нарушений: изменённый native prefix/шестой
  байт окна, короткая строка, пропущенное/дублированное чтение, чужой номер прохода,
  несовпадение summary/raw — все отклонены. Седьмой байт window-only чтения
  закономерно вне шестибайтового scope. Архивные файлы не менялись.
- Первоначальный одноразовый diagnostic пытался разобрать `0x44` через fromhex;
  исправлен формат чтения исходных токенов через int(base16), данные не исправлялись.

**Не закрывается ни DDIC-возможность, ни R3.** Закрыт только вывод «по длине и
повторам уже можно назвать эти байты gamma/CMDQ и выбрать PWM-множитель».
Следующим выполненным офлайн-переходом стал анализ client-rate → ADC-mode у
STK6A2X: [отдельный результат](../flicker_rate_reachability_20261107/result.md).
Он нужен для проверки измерительного канала, не подменяет изменение OLED.
