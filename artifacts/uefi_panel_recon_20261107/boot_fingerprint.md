# Можно ли определить UEFI-вариант по сохранённым DDIC-чтениям?

`confirmed-on-target` **только** для выбранного Android BOE v4 DT и уже сохранённых
четырёх архивов чтений; `confirmed-other-device` для XML из GLOBAL64 XT2611-3;
исполненный на XT2611-1 загрузочный вариант, физическая ревизия и PWM Hz —
`unknown`. Никаких новых чтений панели не выполнялось.

Проверяемая гипотеза: записи, различающиеся между BOE ILI97701A UEFI v0–v4,
но не перезаписанные в выбранных Android v4 командах, могут служить отпечатком
исполненного загрузочного XML в уже сохранённых регистрах. Воспроизводитель —
[`boot_fingerprint.py`](boot_fingerprint.py), компактные счётчики и адреса —
[`boot_fingerprint.json`](boot_fingerprint.json). Входы: сохранённые GLOBAL64 XML
из `.../uefi-panel-recon-20261107/global64/display/`,
[`selected_boe_v4`](../device_tree/selected_boe_v4/) и четыре *полных*
4864-адресных словаря в [`ddic_regdump_20261107`](../ddic_regdump_20261107/).
Сокращённый `s0_probe` и прерванный `s1_aborted_sleep` в сравнение не входят.

Сравниваются последние **payload-записи** по `(page,opcode)`, а `FF 5A A5 xx`
считается только переключателем страницы, не записью регистра `FF`. Условная
«перезапись Android» объединяет **только три** массива: v4 `timing@0/on-command`,
`dc-off-command`, `timing@0/timing-switch-command`. Совпадение UEFI v4 init с
сохранённым selected DT проверяется пакетом за пакетом. Утверждения, что все три
массива действительно исполнились после конкретного UEFI-профиля, здесь нет.

| Отбор | Число адресов |
|---|---:|
| Различается запись или её наличие между v0–v4 | 96 |
| Входит хотя бы в один из трёх выбранных Android-массивов | 53 |
| Не перезаписан в этих трёх массивах | 43 |
| Из них отсутствует среди адресов архивных полных чтений | 25 (`page 2F`) |
| Остался адрес с архивным чтением | 18 |

Дополнительная проверка границы overlay: разобраны **все 52** выбранных DT
packet arrays (1101 пакетов), а не только три выше; 4-байтовое скалярное
`qcom,mdss-dsi-te-dcs-command` исключено. Ни один из остальных 49 массивов
не записывает ни один из **43** оставшихся variant-dependent адресов, включая
все 18 адресов с архивным чтением. Поэтому расширение *условного множества
возможных записей* с трёх до всех 52 массивов сохраняет счётчики 53/43/25/18.
Это не утверждение, что все массивы исполнялись: другие runtime writers,
reset и реальное состояние DDIC по-прежнему неизвестны.

Воспроизведение этого дополнительного отбора из тех же сохранённых файлов:

```sh
PYTHONDONTWRITEBYTECODE=1 python3 - <<'PY'
import sys
sys.path.insert(0, 'artifacts/uefi_panel_recon_20261107')
import boot_fingerprint as b
from audit_pwm_archive import parse_packets
init = [b.writes(b.xml_init(b.CACHE / f'{b.PREFIX}{i}.xml.raw')) for i in range(5)]
keys = set().union(*(set(w) for w in init))
changed = {k for k in keys if len({w.get(k) for w in init}) > 1}
files = sorted(p for p in b.PANEL.rglob('qcom,mdss-dsi-*-command')
               if p.name != 'qcom,mdss-dsi-te-dcs-command')
packets = [parse_packets(p.read_bytes()) for p in files]
all_writes = set().union(*(b.writes(p) for p in packets))
assert len(files) == 52 and sum(map(len, packets)) == 1101
assert len(changed) == 96 and len(changed & all_writes) == 53
assert len(changed - all_writes) == 43
print('PASS: 52 arrays / 1101 packets, no further variant-address writes')
PY
```

Из 18 адресов пятнадцать `page 51` записывает только эталонный **v0** (по шесть
байт); первые шесть архивных байтов совпадают с v0 на **четырёх** адресах во
всех четырёх архивах и не совпадают на остальных **11**. Например, v0 пишет
`51:82=44 44 56 7A 22 22` и `51:83=7A 7A 7A 7A 22 22`, тогда как сохранённый
префикс обоих адресов равен `7A 7A 7A 7A 22 22` в каждом из четырёх архивов.
Ещё три адреса `63:F8/F9/FA` записывает только эталонный **v3** (16 нулевых
байтов), архивные префиксы также нулевые. Ноль может быть исходным/default или
артефактом транспорта и **не подтверждает v3**. У v3-специфичной `page 2F`
таблицы нет архивных чтений.

Отсутствие записи у варианта не означает известное исходное значение DDIC.
Старый 40-байтовый reader не удостоверяет фактическую длину ответа и мог
смешать полезные байты с CRC/пустым хвостом; см.
[`ddic_response_framing_20261107`](../ddic_response_framing_20261107/result.md).
После UEFI могли действовать и иные writers/reset, а XML GLOBAL64 не является
доказательством текущего bootloader владельца. Поэтому этот ограниченный тест
**не идентифицирует** реально исполненный UEFI-вариант: лишь исключает простое
побайтовое объяснение всех сохранённых `page 51` префиксов неизменённой v0
таблицей при допущении корректного readback. Он не декодирует DDIC period/count,
не подтверждает и не исключает OLED PWM≥2000 Гц.

Независимое офлайн-ревью пересчитало все пять XML и три бинарных массива другим
парсером, подтвердило счётчики 96/53/43/25/18, четыре совпадения и 11
несовпадений v0-префиксов, три нулевых v3-префикса; блокирующих замечаний нет.
Воспроизводитель/JSON дополнительно сверены побайтно в Python normal/`-O`.

Воспроизведение (только сохранённые файлы, output должен отсутствовать):

```sh
PYTHONDONTWRITEBYTECODE=1 python3 artifacts/uefi_panel_recon_20261107/boot_fingerprint.py OUTPUT.json
```

R3 остаётся активной. A9-only — лучший промежуточный panel baseline
([архив](../dsi_selector_split_20261107/result.md)), не измерение Hz. Для
причинной пробы A0D1C1 действует [отдельная точная граница
согласия](../dsi_coupled_9d_20261107/proposal.md); HORIZON и офлайн-сверка
не являются разрешением отправить новый DSI-профиль.
